# Agent Note: 观测存档与召回——纯文本存档 + 可重建 FTS5 + 只读 recall 工具（默认 off）

Status: implemented

## Problem

薄环的观测历史在上下文里是**滚动丢弃**的：图片剪除只留最新 K 条含图消息，OBS marks 折叠把更早的
digest 压成一行占位（[P0 #3](../../../AGENTS.md)）。这换来稳定的上下文成本，但也留下一个空白：模型
想回看几步之前那一屏的细节（价格、验证码、列表项、按钮文字），只能依赖 transcript 里残存的折叠行，
而折叠行没有 marks，帧与帧之间也没有可检索的索引。多步任务里"刚才那屏到底有什么"是真实且高频的
需求，缺通道时模型只能重新导航回那一屏——多花步数，还可能因为界面状态变化而回不去。

约束同时来自四条军规与两条装配契约：

- 观测只有一个生产者 `session.observe()`（P0 #15）——不能为存档另开截图/dump 路径；
- 执行动作必须绑定当前批次的 mark（P0 #2）——历史帧里的 mark id 不能重新变成可寻址目标；
- 截图 base64 的落盘边界是绝对的（P0 #6 的隐私口径）——存档不能成为第二条图片落盘面；
- 能力默认关闭时必须零行为变化，启用时也必须 fail-open——存档坏掉不能影响任何一次 run；
- trace 是脱敏面（文本截 64 字）：存档需要一个自己的、本机私有的落盘面。

## Decision

新增内建能力 `obs_archive`（`PHONE_AGENT_OBS_ARCHIVE`，默认 `off`），边界如下：

- **写入**：唯一生产者 `observe()` 提交成功时，调用 capability 安装在 session 上的 fail-open sink；
  sink 用**同一个**模型可见渲染函数（`format_observation_text`）生成 `[OBS]` 文本，连同
  `run_id`/`epoch`/`screen_seq`/前台包名/时间戳写入 `<obs_archive_dir>/<run_id>.jsonl`（默认
  `memory/obs_archive`）。观测失败（含未验证参考图）不写。
- **纯文本**：只落文本。截图、base64、图像 hash 都不进存档——存档是"模型当时看到了什么文字"的
  副本，不是第二份屏幕像素。理由：隐私边界（P0 #6 的同一 threat model）与体积成本都不允许图片。
- **索引**：每个 run 一个 SQLite **FTS5** 表（`<run_id>.db`），技术族与 `v2/recall.py` 的关键词
  通道一致但不引嵌入（存档检索要的是确定性、零模型依赖）。索引是派生态：meta 表记录 jsonl 字节数，
  缺失/损坏/外部追加时从 jsonl 重建，jsonl 始终是真相。
- **读取**：能力挂载时只注册两个只读工具。`recall_screen(screen_seq, offset, limit)` 按行分页回看
  一帧；`search_screens(query, limit)` 在本 run 存档内做 FTS 检索，返回命中帧号与短摘要。两者都不
  碰设备、不铸 mark、不改 `session.marks`。
- **失效渲染**：回执里每个历史 mark id 一律改写为 `历史:ax_3@e12（已失效）`（含 locate 铸的
  `la_1#2@e11` 形态），工具说明与回执都写明"历史证据、不能作为执行目标、要操作请重新 read_screen"。
- **提示**：图片剪除的 marks 折叠占位仅在能力挂载期间追加 `[可 recall_screen]` 后缀；未挂载时
  占位文本逐字节保持原样（默认关闭 = 零行为变化）。
- **保留**：`PHONE_AGENT_OBS_ARCHIVE_KEEP_RUNS`（默认 20）按 jsonl mtime 保留最新 N 个 run，
  更老的 jsonl 与其 db（含 WAL/SHM 边车）在下次写入时整体删除，当前 run 永不删。
- **失败面**：写入侧 fail-open（错误只以事件名进 trace 诊断，绝不上抛）；读取侧返回诚实错误文本，
  并且**不**因为存档不可用而改变当前屏幕的可执行状态。
- **归属**：新模块 `v2/obs_archive.py`（存储/索引/失效渲染）与 `v2/tools/obs_archive.py`（工具）；
  run_id 由 harness 工厂（`agent.py::obs_archive_factory`）提供，capability 只做装配与安装。
- 明确不做：不投影到 Web 控制台；不写 trace 正文；不做跨 run 检索；不做截图/缩略图存档。

## Alternatives considered

- **提高 `PHONE_AGENT_OBS_MARKS_KEEP` 把完整 digest 留在 transcript 里**
  - **最强的理由**：零新存储、零新工具，模型直接可见，实现成本最低。
  - **为何被否**：token 成本随步数线性上涨，直接顶撞上下文工作目标；更糟的是历史 mark 留在上下文里
    会持续诱导对过期批次寻址（resolve_mark 会拒，但每次拒绝都是一次失败的模型步）。历史证据应该是
    **按需拉取**的，而不是常驻的。
- **全局单库索引（跨 run 可搜）**
  - **最强的理由**：一次建库复用到所有 run，"过去跑过的类似屏幕"检索只需放宽 WHERE，还能省掉每次
    重建。
  - **为何被否**：本契约的检索范围是"本 run 的存档帧"；跨 run 会把不同设备/账号的屏幕文本混进同一个
    检索面，隐私与保留策略都更难守（按 run 整删变成按行删除）。per-run 文件 + 整删更简单、可验证。
- **复用诊断证据流（`outputs/live-diagnosis/.evidence`）**
  - **最强的理由**：已有实现、已有 schema，零新落盘面，包含全文本证据。
  - **为何被否**：诊断证据流是"诊断会话"的临时产物（默认 off、由技能开关、面向事后分析），不承诺
    运行期可读，也没有跨 run 保留/淘汰契约。把运行期 recall 工具绑到它，等于把诊断面临时性语义
    偷换成记忆面语义。
- **回执里保留原始 mark id 让模型直接复用**
  - **最强的理由**：忠实回放最省认知成本；模型看惯的 `ax_1@e12` 形态不用二次翻译。
  - **为何被否**：违反 marks-first 的根因防线——两帧的 id 串可能相同（provider 重新从 1 编号），
    照抄旧 id 在下一批里"恰好命中"是本可避免的误击。`历史:…（已失效）` 前缀 + 后缀让误用在结构上
    不可寻址，且渲染是幂等的。
- **归档截图缩略图（视觉回看）**
  - **最强的理由**：有些帧的价值在像素（图片内容、不可访问控件），文本回看天然缺失。
  - **为何被否**：图片落盘把隐私与体积边界从"模型可见文本"扩大到"屏幕像素"，与 P0 #6 的取向冲突；
    本能力的定位是"文字证据回看"，不是第二套视觉记忆。

## Consequences

- **收益**：跨步回看从"重新导航"变成一次显式只读调用；recall 证据与执行 authority 在结构上分离
  （历史 id 永久失效）；默认 off、零成本、零行为变化；任何存档/索引/召回失败都不影响 run。
- **代价**：存档复制了模型可见文本（含屏幕文字），默认虽在 git-ignored 的 `memory/` 私有目录，仍是
  敏感数据，部署者需要理解保留窗口；FTS 索引是派生态，首次打开有一次性重建成本；检索只看当前 run，
  跨 run 的"相似屏幕"检索需要重新设计索引布局；`capabilities.py`/`agent.py` 各多一个挂载点，与并行
  改动共享这两个装配热点。
- **仍然脆弱**：留存排序按文件 mtime（时间穿越/批量拷贝的场景排序不代表真实新旧）；索引只有在
  打开时才验证，进程内被外部改写不会立刻发现；`search_screens` 的关键词分词与 `recall.py` 同族但
  各写一份，未来若统一 tokenizer 需要同批迁移两处。

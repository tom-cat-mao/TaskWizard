# Agent Note: 覆盖率进 CI 报告但不设阈值，test job 只报告不卡线

Status: implemented

## Problem

三道门禁（[2026-09-15-ci-three-gate-pipeline.md](2026-09-15-ci-three-gate-pipeline.md)）里的 test job 目前只产出
一个二值结论：1815 个断言过没过。它对「测试到底跑到了哪些代码」完全沉默——删掉 `phone_agent/web/app.py` 的
一个分支、或新增一段从未被调用的逻辑，在当前 CI 眼里是同样的绿。裁决者因此少一个客观信号，只能靠读 diff 的
长度估风险；而并行 agent 越多，这个估计越不可靠。

同类问题在别的项目里已经有现成解法：按文件 100% 覆盖硬卡（DSH 的流水线就是这么做的）。这条事实是本次取舍的
起点——**要不要照搬**。

## Decision

- **收覆盖率，但绝不设阈值**：test job 的 pytest 命令加 `--cov=phone_agent --cov-report=term-missing
  --cov-report=xml:coverage.xml`，3.12 / 3.13 两条腿都收。**没有 `--cov-fail-under`，也不允许以后加**：
  这是本决定的核心边界——任何覆盖率数字都不构成 job 变红的理由。
- **两个可见面**：`$GITHUB_STEP_SUMMARY` 里一张「总覆盖率 + 每个子系统一行」的 markdown 表（两条腿都写）；
  3.13 腿额外上传 `coverage-3.13` artifact（`coverage.xml`）。摘要步骤挂 `if: always()` +
  `continue-on-error: true`：跑红了也出报告，报告自己坏了也不许把 job 弄红。
- **聚合口径按子系统，不按文件**：`v2`、`web`、`grounding`、`adb`、`config` 与包顶层文件各一行。85 个文件
  逐行列表没人读；评审要看的是「哪个子系统没被碰到」，不是「哪个文件差 3 行」。
- **不新增 `.coveragerc`**：仓库没有 `pyproject.toml`/`pytest.ini`/`setup.cfg`，而 `--cov=phone_agent` 的默认
  行为本机实测已正确（未导入的模块按 0% 计入、无 omit 缺失告警、总数与 coverage 自带 TOTAL 一致），加配置
  只会多一个需要同步的表面。
- **锁文件补两行**：`pytest-cov==7.1.0` 与它的唯一运行时依赖 `coverage==7.16.1`，按字母序插入
  `requirements.lock`。只钉 `pytest-cov` 而放开 `coverage`，等于把「依赖漂移」这个已经击穿过一次 CI 的洞
  重新打开——这个文件是 CI 的确定性真相源，不是人类可读的范围文件。

## Alternatives considered

- **照搬 DSH 的「按文件 100% 硬卡」**
  - **最强的理由**：零注水空间。阈值一旦是「按文件 100%」，就没有「提高数字但不测行为」的余地——每个文件的
    每一行要么被执行到、要么 CI 红，覆盖率与「真的测过」在此定义下等价。这是所有覆盖率策略里唯一不需要
    额外信任的，也是它在本仓之外能长期活着的原因。
  - **为何被否**：本仓库当前总覆盖率 82.8%，缺口集中在按设计就很难单测的地方——`web` 41.6%（NiceGUI 界面
    装配，`app.py` 一个文件 905 个语句、18% 被跑到）、`adb` 64.5%（贴设备协议）、`grounding` 65.4%
    （视觉定位）、包顶层 45.7%。补齐这些边角测试的成本远大于收益；按文件 100% 更极端。**更糟的是激励**：
    硬卡之下，写 `assert True` 式假测试是「合规」成本最低的路径，而评审者无法从绿灯里区分真测试与假测试——
    门禁会从「保证质量」退化成「保证数字」。研究型项目里，后者的代价高于前者。
- **完全不看覆盖率**
  - **最强的理由**：零新增维护面、零新增 CI 时间。它也不假装自己有用——覆盖率只证明「行被执行过」，不证明
    断言有效（一个 `assert True` 同样能推高数字），所以它天然是弱信号；不看它就没有被弱信号误导的风险。
  - **为何被否**：评审 PR 时少一个客观信号。人读 diff 只能估计「改动看起来不大」，而覆盖分布能直接回答
    「这个 PR 动的子系统有没有被这套测试碰到」。它不必是决定性的，但它是**发现「新增了零测试模块」的最低成本
    手段**——缺了它，一个完全没测试的新子系统在 CI 上与测试充分的改动毫无区别。

## Consequences

- **收益**：每个 PR 首次出现一份不由产出方书写、也不由产出方选择的覆盖分布；评审从「读 diff 猜风险」变成
  「看哪个子系统没被碰到」。因为没有任何阈值，这个数字不需要被辩护——它只用来提问，不用来判罪。
  本地与 CI 共用同一条 pytest 命令，所以「我本地跑绿了」与云端报告之间不再有解释空间。
- **代价**：CI 时间是双份的，两条矩阵腿都跑覆盖率。本机同一套 1815 个测试实测：无覆盖 62s、带覆盖 78s
  （墙钟约 +26%）；CI runner 上未实测，量级应相近，test job 的两条腿各自承担这份增量。覆盖率运行还会把
  `.coverage` 与 `coverage.xml` 写进工作区（`.coverage` 已被 `.gitignore` 忽略，`coverage.xml` 没有）。
  `coverage.xml` 的 `<sources>` 记录检出目录的绝对路径，它随 artifact 上传，但 artifact 仅在仓库内可见，
  不进 Pages、不进 PR 评论。**报告可能被无视**：step summary 默认折叠在 job 页面里，评审者不点开就等于没有；
  artifact 只有 3.13 腿一份，看 3.12 腿的人看不到附件。两者都不影响正确性，但都意味着这份数据的实际价值
  取决于是否有人看。
- **仍然脆弱**：覆盖率只度量行是否被执行，不度量断言是否有效，也不区分「测试验证了这个分支」与「测试恰好
  路过了这个分支」。因此它不能替代真机验收，也不能替代人读 diff——它是第 4 个信号，不是第 4 道门禁。

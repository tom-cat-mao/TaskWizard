# Agent Note: 路线边界触发折叠——信号归模型、决定归 harness，并复用同一条折叠路径

Status: implemented

## Problem

容量触发的 auto-compact（T1 预警 / T2 强制）只在估算上下文逼近窗口时才折叠。这有两个代价：

1. 折叠前每一次请求都按全量历史付费——省下的只有之后的步数；
2. 切点由 token 计数决定，落点可能把「一个刚做完的子任务」从中间切开，摘要因此既丢了
   该子任务的完整叙事，又留下半截无用的相邻动作。

同时观察到的事实是：模型自己在 TaskDoc 上维护路线项，而 P0 #11 保证完成必须经
`in_progress → completed`。也就是说「一段有意义的工作结束了」这个事件在 harness 侧本来就可
见，只是没人用它。缺的从来不是信号，是一个不做工作流路由的用法。

另一处独立的问题：交接摘要的质量无人知晓。摘要模型可以把没发生过的说法写进摘要，折叠照样
提交，之后无人可查——历史上没有任何关于「摘要有多少是逐字搬运、多少是外推」的数字。

## Decision

**信号由模型给，决定由 harness 做。** `update_task_doc` 提交成功且出现 `in_progress → completed`
迁移时，发内建事件 `taskdoc/completed`（payload `{"item_ids","screen_seq","epoch"}`，fail-open，
不改动回执）。新能力 `boundary_compact`（`cap_id=boundary_compact`，挂在 compact 之内）监听它，
记下这个边界覆盖了多少观测；在下一个 `model/pre_request` 检查点做纯机械判断：

- `horizon = 未完成路线项数 × 每条路线项平均步数`；平均步数在本 run 内实测（观测数 / 完成项
  数），完成项数不足 `SAMPLE_GUARD_ITEMS`（默认 2）时用先验 `STEPS_PER_ITEM`（默认 4）；
- `benefit = (区间 token 估算 − 摘要 token) × horizon`，`cost = 区间 token + 摘要 token`
  （即一次摘要调用的输入加输出，摘要上限取 `PHONE_AGENT_COMPACT_SUMMARY_TOKENS`）；
- 只有 `benefit ≥ MIN_NET_RATIO × cost`（默认 1.5）且区间、horizon 各自过下限才折叠，否则记录
  推迟原因。估算全部走 `middleware/_tokens.py`，不引入第二套计量。

明确不做：不新增计划工具，不猜工作流，不因为「看起来像边界」就折；窗口压力与物理容量折叠
（T2）始终优先且完全不属于本能力的管辖——监听器注册在 compact 之内，容量折叠刚折过的检查点上
本能力无事可做。**一个边界至多一次决策**，推迟就交给 T2 兜底，避免逐步重试造成抖动。

**复用既有的折叠路径，而不是另写一条。** `compact.py` 里把提交段（规模下限、保护组准入、摘要
预算、重建后度量、净缩减阈值、失败保留基线）抽成唯一一处 `_commit_fold`，容量触发与新的公开接缝
`CompactMiddleware.request_semantic_fold(messages, *, span_hint=None)` 共用它；`span_hint` 是「边界
之后要逐字保留的轮数」，切点因此落在子任务边界上而不是 token 计数上，并且仍被夹到最早的保护轮
之前——边界只能在不违反保护规则的前提下加宽折叠。返回值是纯的完整消息列表（不发
`RemoveMessage`，符合 `model/pre_request` 契约）。差异只在接受规则：边界折叠要求放得下且确实
净缩减，不要求达到容量路径的低水位目标。

**默认 `shadow`。** 决策照常计算、照常落 `boundary_compact_decision` trace，但监听器把原列表
原样交给 `next`——对象同一，不产生任何重写。这与 `memory_rag` / lesson 注入的 shadow 军规同形
（P0 #16a）。

**摘要逐字命中影子指标（第 C 项）。** 每次成功折叠在提交前机械统计：摘要里实质性行（跳过
标题、过短行，最多 40 条）有多少能在被折叠区间的原文里逐字命中，落 `compact_summary_quote_check`
（计数、命中率、至多 3 条本地裁剪到 60 字的未命中样本）。指标只统计模型写的正文，不含 harness
追加的确定性「记忆与能力」尾注。纯观察：无闸门读取，采样器抛错不影响折叠，折叠被既有原因中止
时不发事件。

## Alternatives considered

- **给模型一个显式 plan/subtask 工具（对齐 SoL-Pi 的做法）。**
  - 最强的理由：边界语义精确，不必从任务板迁移反推，还能带上预期步数。
  - 为何被否：thin-loop 的立身之本是 harness 不做工作流路由（根 `AGENTS.md` "What This Is"），新增计划工具等于把流程语义请回来；而 TaskDoc 的迁移已经是被 P0 #11 强制的真实边界，多一个工具只是多一份可以撒谎的输入。
- **让模型自己决定何时压缩（把判断做成提示词规则）。**
  - 最强的理由：模型知道自己刚做完什么，判断成本为零。
  - 为何被否：它无法估算 horizon 与 token 价格，会把「感觉该总结了」当成决策依据；折叠一旦可被模型触发，也就成了可被诱导的行为。harness 侧的数字至少可复算、可测。
- **另写一条轻量折叠函数给边界用。**
  - 最强的理由：容量折叠那套闸门很沉，独立实现更直观。
  - 为何被否：两条折叠路径必然漂移——保护组、净缩减、fail-soft 只要有一边漏掉，就是「边界折叠悄悄丢掉了最新观测或 TaskDoc pin」这种最难查的缺陷。共用 `_commit_fold` 让闸门只有一处真相。
- **horizon 用固定常数（例如恒按 5 步）。**
  - 最强的理由：无需统计，行为完全可预测。
  - 为何被否：它把「任务还剩几步」这个最关键的量变成与任务无关的常数，长任务永远折叠、短任务永不折叠。实测均值 + 小样本退回先验只是把同一个量锚在真实数据上。
- **指标做成语义相似度（嵌入比对）。**
  - 最强的理由：能识别换词改写，覆盖面更广。
  - 为何被否：需要再引入一个模型调用与一套向量口径，观察指标不该有成本与不确定性；逐字命中率恰好是想要的信号——摘要里有多少是从原文照搬的。

## Consequences

- **收益**：折叠时机从「窗口快爆」前移到「一段工作结束」，省的是整段后续步数的全量付费；切点对齐子任务，摘要叙事完整；默认 `shadow` 使合入零风险，真机数据先于开关落地；摘要有了第一个可离线统计的质量数字；`off` 时代码路径与合入前完全一致。
- **代价**：多一个内建事件与一个能力（内建能力从十一变十二，装配表、事件表、嵌套顺序需同步）；判断建立在「一步 ≈ 两条消息、平均 token/消息」这类粗估上，噪声大——所以只有明显划算才折；小样本退回先验时可能长期停在 4 步/项，长任务会低估 horizon 而推迟折叠（偏保守方向是可接受的偏差，因为 T2 仍会兜底）；`on` 档每个边界至多尝试一次，最多付一次摘要调用；`compact.py` 的公共接缝与内部重构使该文件成为并发分支的冲突热点。
